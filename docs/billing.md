# 扣费来源与额度可用量预估

## 公式与单位

```text
有效单价（分/Mtok）= 已知扣费积分合计 ÷ 同口径 token 合计 × 1,000,000
预计 token = 模型可用余额 ÷ 有效单价 × 1,000,000
```

“分”是对应平台的积分展示单位，不是人民币分。不同平台的余额不能互兑；同平台各模型通常共享余额，各行是独立消费情景，不能相加。

估值沿用样本时的输入／输出比例、缓存、区域和折扣，不是固定官方价格。当前不会按思考档位分别定价。目录倍率、参考 `cost_cny` 和实际积分结算是不同概念。

## 来源

| 平台 | 余额来源 | 模型单价来源 |
|---|---|---|
| WorkBuddy | 引擎账号积分；按模型可用区域取余额 | 国内／国际最近用量中的模型实扣合计与 token；当前混区计价 |
| Qoder | 引擎账号积分 | 最近用量中同模型的实扣与 token |
| 千问办公 | 账号 resources 钱包与余额快照 | 钱包均价校准短样本相对价，非逐请求实扣 |
| 小浣熊 | `/panel/api/overview` | 请求事件与按账号只读积分账单的唯一关联 |
| Trae | 引擎归一的 entitlement 积分／权益余额 | 优先逐请求 `credit/credits`；缺失时用官方消费倍率 × 钱包快照反推的平台均价 |

只对启用的平台估值。余额未知或某个启用账号未报告余额时，不把已知部分伪装成完整余额；输出里保留覆盖数量。停用平台从目录、轮询与估值中排除。

## 小浣熊：与 WorkBuddy 共用实扣估算

小浣熊和 WorkBuddy 使用相同的统计函数与样本门槛：每个模型以有效请求的 **Σ实扣积分 ÷ Σtoken × 1,000,000** 计算单价，再用余额换算预计 token。两者都至少需要三条有效扣费记录、累计 500 token 且总扣费为正。大请求照常计入加权汇总，不因单条占比较高而剔除；模型样本不足时保持待测，不借用其他模型的单价。

两者区别在扣费数据的取得方式。xhx2api 请求事件包含请求编号、账号、模型和 token；积分账单包含金额与事件名称，但没有可靠的模型字段。因此先把账单唯一关联到请求，得到与 WorkBuddy 用量行同口径的实扣记录，不能按时间接近、模型倍率或余额下降任意分摊。未关联的请求，其扣费和 token 都不进入单价的分子、分母。

Gateway Hub 对未提供 `title` 的新 Chat Completions 请求生成随机标记作为账单标题，并记录与引擎响应 `X-Request-Id` 的关联。客户端已有标题会原样保留，不强行纳入标记对账。该元数据文件不保存提示词或密钥。后台估值读取固定的账号账单 GET 接口，只有关联证据充分时才为请求补充实际积分。

- 历史没有标记的请求保持未知，不自动回填。
- 多笔消费、重复或含糊关联不会强行选一笔。
- 账单查询失败、尚未结算、引擎未返回请求编号或日志缺失，都会导致样本不足。
- Responses 等入口可能在引擎转换时丢弃 title，不保证具有相同账单关联能力。
- 账单查询有缓存与条数上限，不是完整财务台账。
- 图片通道的积分／张与聊天 token 单价分开，不能混算。

标题回显行为来自所核对的 xhx2api 实现；实际服务端未回显唯一标记时，结果仍是待测。离线测试通过不等于已经完成真实账单端到端核验。

## Trae：明确报告与缺失分开

Trae 引擎旧实现会把没返回扣费的请求也写成 `credit=0`。`usage_missing=false` 只说明 token usage 存在，不能证明 credit 同样存在。

网关估值只接收：

```text
usage_missing != true
credit_reported == true
credit 为有效、非负数字
```

`credit_reported` 是上游引擎记录器必须提供的字段。兼容记录示例：

```json
{
  "model": "example-model",
  "total_tokens": 1000,
  "credit": 1.25,
  "credit_reported": true,
  "usage_missing": false
}
```

真实报告零扣费可以标为 `credit_reported=true`；未知值不能这样标。整批全部免费仍不会算出一个可除的正单价。

本仓库不包含或自动安装 Trae 引擎的修改。若使用的引擎版本没有记录这个标记，旧请求继续待测；需要在引擎接收原始 usage 时区分 `credits/credit` 键是否存在，不能从后来的默认零值倒推。参考人民币成本不能作为补齐积分的方法。

### Trae 钱包快照兜底

实测 trae2api-hub 当前版本对所有请求都写 `credit_reported=false`，逐请求实扣这条路走不通。网关因此补了一条兜底：

1. 每次 `/api/status` 轮询把 Trae 账号余额写入 `trae_wallet_history.jsonl`（运行态文件，已在 `.gitignore`）。
2. 只用**余额真正下降**的相邻快照区间，把该区间的余额差 ÷ 同期 token 反推平台均价（分/Mtok），与千问办公同一口径、同一样本门槛（≥10 万 token、余额必须下降）。静止期（余额是缓存值）不计入，避免把一次性扣费摊到整段窗口上稀释出假单价。
3. 模型间按官方 `features.consumption_rate.data.rate`（如 DeepSeek-V4.1-Flash 0.06、Kimi-K3 1.83）分配相对差异，再乘平台锚定系数。

优先级：上游若真的报告了 `credit_reported=true` 的扣费，仍以实扣为准，倍率只在缺失时使用。

已知限制：

- 快照键用 uid 尾 4 位（引擎 `/accounts` 把 uid 脱敏成 `…4052`，usage 行里是完整 uid），同一尾号多账号会合并。
- 余额下降同时可能有发放/充值，`_wallet_rate` 只跳过余额增加的区间，无法识别「同区间既扣费又充值」。
- 只有一份快照、或区间内 token 不足时继续显示「钱包快照样本不足，无法锚定」，不会猜一个数字。

## 积分过期时间

看板「即将过期的积分」是平台无关的时间轴，各平台来源不同：

| 平台 | 来源 | 说明 |
|---|---|---|
| WorkBuddy | `credits.earliest_expiring` | 引擎已算出最临期包与 `days_left` |
| Qoder | `credits.expires_at` | 整池到期（套餐 + 签到包） |
| 千问办公 | `config.json` 的 `qwenwork_reset_at` | 上游不透出，用户手填按月重置日 |
| 小浣熊 | `GET /panel/api/points` 的 `audit.expire` | 积分有效期，秒级时间戳 |
| Trae | 权益包的 `expire_time` | 逐包到期，跳过 `is_hide` 与已用尽的包 |

**「距过期」与「按当前速度可用」是两件事，不能混用一列。** 小浣熊的 `audit.days_left` 是 `remain ÷ burn_per_day`（按近期燃烧速度还能用多久），实测 9421 点对应 374.7 天，而积分本身 6.4 天后到期——把前者当到期天数会显示「还剩 374 天」，实际一周后清零。因此网关的 `days_left` 一律由到期时间现算，速度预测单独放在 `burn_days`，看板分两列展示。

到期时间戳单位不统一（小浣熊积分到期是秒、其 overview 的凭证 `expires_at` 是毫秒、Trae 的 `expire_time` 是秒），统一经 `_epoch_seconds` 归一并丢弃越界值，避免 Windows 上 `localtime` 抛错毁掉整平台聚合。

小浣熊的 `/panel/api/points` 是附加信息：该接口失败只让临期行缺省，不影响账号与余额聚合。

## 样本门槛

逐请求计价至少需要三条有效行、累计 500 token 且总扣费大于零。达到门槛只是允许计算，不表示统计已稳定。千问钱包均价还要求账号有两个可用快照、正净扣费和至少 100,000 个同期 token。

千问短样本价表只是相对价参照；缺少价表或钱包锚点时不估。长期无请求、钱包发放／重置或观测窗口被裁剪时，原先可算的锚点也可能暂时丢失。

## 验证与隐私

离线回归使用合成数据核验来源标记、缺失、重复、账号和时间边界；不读取真实凭证、不生成付费模型请求。真实账单对账需另行观察正常使用产生的数据。

运行态的 `config.json`、账号目录、日志、账单关联和余额历史都应留在本机，不上传公共仓库。仅查看余额和正常生成也可能触发各引擎自己的缓存或持久化行为，应以引擎实现为准。
